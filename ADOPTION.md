# Adoption and maintenance

**Release candidate:** 0.2.0 draft. The framework is authored, not adopted by a real organisation. The delivery package does not create a remote GitHub repository or live integrations.

## Before a public release

1. Confirm the repository owner, named maintainer(s), reviewers, distribution terms and contribution arrangements. Resolve [rights status](RIGHTS.md); no licence is selected automatically.
2. Review both runbooks, source ownership and high-level process boundaries. Refresh source routes and examine unresolved dependencies before making material claims.
3. Run [structural validation](validation/README.md) and review affected acceptance scenarios. Inspect Markdown with the intended reading/assistive-technology setup; structural validation is not accessibility user testing.
4. Record actual release date/version/commit, known limitations, source verification scope and migration notes. Do not present a draft as an operationally proven programme.

## Before organisational adoption

Complete the organisation profile and map role functions to actual people/delegation. Confirm applicable obligations and commitments, data controls, capacity, permitted AI tools/actions, existing governance, support routes and source baselines. Approve the actual programme through normal authority. Do not require additional committees when existing governance can fulfil the function.

## Pilot

Choose bounded employee/customer activities with affected people and operational teams. Agree intended outcomes, evidence, access arrangements, privacy, time/capacity, recovery and review. Evaluate both human-only and selected AI-assisted use where useful. Record error/correction rate, verification burden, useful time released, missed barriers and actual participation outcomes. Independent human review and a pilot remain pending in this release.

## Maintain

- Source changes: follow framework/source-use-and-change.md and trace used_by relationships.
- Process changes: preserve P/E/C/R IDs; record meaningful behaviour changes and migration implications in CHANGELOG.md.
- Catalogue changes: maintain sources/catalogue.yaml, regenerate its Markdown view and recheck links.
- Workflows: keep YAML and Markdown aligned; definitions do not enforce permissions.
- Feedback: make contribution and barrier-reporting routes accessible. Select the actual repository issue/contact route on publication; no unverified address is supplied here.
- Reviews: use locally agreed risk-based intervals plus law/policy, supplier, model, component, organisation, audience and incident triggers.

Use normal organisational systems for real evidence, authentication, permissions and audit records. A private fork or approved workspace may hold local adaptations; do not publish confidential case data through examples, pull requests or issues.
